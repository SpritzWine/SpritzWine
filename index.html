Sanely adding value to Wine, leveraging Rust.

A G’spritzter is wine cut with soda — same wine, just easier to get along with. SpritzWine is that, for the other Wine: take the Wine your games already run on, mix in Rust exactly where the C has been quietly ruining afternoons — parsers, descriptors, unwinders — and leave the rest in peace.

This is the superproject — where the Wine fork and the Rust workspace are developed together. Not what you install to play a game: that is Prater.

The approach

Think big, act small.

The ambition is real: Wine is a thirty-year-old C codebase, and large parts of it are exactly the kind of code that benefits from stronger guarantees — parsing untrusted bytes, walking descriptors, unwinding stacks. There is value on the table.

The method is deliberately unambitious. Start where it brings real value in safety, performance or correctness — one subsystem at a time, each one shipped and proven on real games. A subsystem is not converted until it is pure; it is converted until the remaining C has stopped being a problem. Then you leave, and go find the next place where the bugs actually live.

Nobody upstream asked for any of this, and nobody’s inbox is being campaigned at. The code sits here — LGPL, working, played on — and if a piece proves itself and somebody wants it, it’s theirs. Demonstrating beats lobbying.

Rust is a means, not the goal. This is not “rewrite Wine in Rust.” Nobody needs that, and nobody would finish it. Rust goes where C is genuinely hurting.
Prove it where it hurts. The destination is upstream Wine. But the proving ground is Valve’s tree — the only one anti-tamper titles boot on — so that is what ships first.
Games are the test suite. Wine’s conformance tests are necessary and not sufficient. The gate is a game booting, not a suite passing.

Under the hood

Soda in, spritzer out.

The Rust code lives outside the Wine tree. Wine’s configure.ac finds the crates via $SPRITZWINE_RUST_DIR; the Wine fork carries only build glue and the C-side bridges. That split is the load-bearing one.

The fork itself is generated, not hand-maintained: the changes are authored once as thematic soda-* tiers and replayed onto a stable Wine base to produce a consumer branch. Where the two disagree, the base wins. The fork is designed to be peeled off.

What ships today

The current pour.

Not everything written is wired in — the tier decides what lands in a consumer. The current pin (spritzvalve-11.0-1 = build + core + branding) links Rust into these:

In the glass right now
ModuleWhat’s in Rust
hidparse.sys the HID report-descriptor parser — a driver, kernel-pool backed
hid.dll the HidP_* value engine — extracting fields out of report buffers
avrt.dll MMCSS — thread scheduling classes
comdlg32.dll the file chooser, via the XDG desktop portal — WoW64-thunked, so 32- and 64-bit apps both get it

Two of those four are literally “parse a byte blob a USB device handed you and index into it,” and a third is a protocol client. That is not a coincidence — it is where you land when the goal is fewer bugs, not more Rust.

The threadpool, the SEH unwinder, LZNT1 compression, battery reporting and DualSense rumble exist too — written, building, deliberately not shipped. Code that isn’t proven on a real game stays in the workshop.

grep -l lwine_ dlls/*/Makefile.in in the wine tree answers this question for whatever you have checked out. Trust that over this table.

Which glass do you want

Pour it yourself.

  • To play games Prater — the Proton distribution. That is the download.
  • To trace one beisl — the performance tracer. Wine-agnostic on purpose.
  • To hack on it this repo — the Wine fork, the Rust workspace, the pins.

The default branch is rust; there is no main. The supported environment is the Fedora dev container under .devcontainer/ — Rust toolchain, the {i686,x86_64}-pc-windows-gnullvm targets, clang, lld and libclang, preconfigured. Everything is LGPL-2.1-or-later: cherry-pick it freely, no permission needed. Source and issues at codeberg.org/SpritzWine/SpritzWine. 

# the superproject: the wine fork + the rust workspace
git clone --recursive \
  https://codeberg.org/SpritzWine/SpritzWine.git

# one-shot: wine (new-WoW64, graphical) + the crates
./build.sh

# -> a relocatable tarball, installer inside
./packaging/package.sh

# what is really Rust in the tree you have:
grep -l lwine_ wine/dlls/*/Makefile.in
